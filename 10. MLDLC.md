# Machine Learning Development Life Cycle (MLDLC)

## What is MLDLC?

Just as **SDLC (Software Development Life Cycle)** gives software engineers a standard set of
guidelines to build any software product from idea to deployment, **MLDLC** is the equivalent
set of guidelines for building any **machine learning–based software product** — end to end,
from framing the problem to maintaining the model in production.

Since ML is used across very different industries (recommendation systems, fraud detection,
mask detection, price prediction, etc.), MLDLC provides a common, repeatable process that
applies regardless of the specific use case.

> A common beginner mistake: training a model, checking its accuracy, and stopping there.
> Building an actual ML **product** requires several more stages beyond just training a model —
> this is exactly what interviewers/companies look for when hiring for ML roles.

MLDLC consists of the following major stages:

1. Frame the Problem
2. Gather Data
3. Data Preprocessing
4. Exploratory Data Analysis (EDA)
5. Feature Engineering & Feature Selection
6. Model Training, Evaluation & Selection
7. Model Deployment
8. Testing
9. Optimization / Maintenance

---

## 1. Frame the Problem

Before doing anything, decide **exactly what problem you're solving**. This stage is entirely
about clarity — jumping in without it leads to wasted work and restarts later.

Key questions to answer here:
- What exactly is the problem? What are you solving for the customer/business?
- What will the final product look like?
- Is this a **supervised** or **unsupervised** learning problem?
- Will the model run in **batch mode** or **online/real-time mode**?
- What kind of algorithm(s) are likely to help?
- Where will the data come from?
- What's the budget and team size required?

Getting clear answers here gives you a mental roadmap for every stage that follows.

---

## 2. Gather Data

Without data, there is no machine learning. Unlike college/practice projects where data is
handed to you or easily downloaded, real-world/company data is often not readily available.
Common sources include:

- **Direct files** — CSVs handed to you directly (simplest case)
- **APIs** — hit an API, fetch data (usually as JSON), convert to your preferred format (e.g., CSV)
- **Web scraping** — when data isn't available via API, scrape it directly from websites
  (e.g., hotel details, pricing pages)
- **Data warehouses** — via **ETL (Extract, Transform, Load)** pipelines when data lives across
  live/operational databases that can't be queried directly
- **Big data / clusters** — when data is too large for a single machine, distributed systems
  (e.g., Spark/Hadoop-style clusters) are used to select and pull relevant subsets

**Goal of this stage:** get the right data into your system in a usable, stored format.

---

## 3. Data Preprocessing

Raw/collected data is almost always "dirty" — it can't be fed directly into an ML algorithm.
Common issues:

- Spelling/typing errors
- Missing values
- Outliers
- Duplicate rows
- Data merged from multiple sources with mismatched formats or differing column counts

**Typical preprocessing tasks:**
- Remove duplicates
- Handle/remove missing values
- Handle outliers
- **Feature scaling** — bring columns onto comparable scales (e.g., one column in the millions,
  another in decimals) so distance-based algorithms aren't skewed

**Goal:** transform data into a clean format your ML algorithm can actually consume.

---

## 4. Exploratory Data Analysis (EDA)

EDA is about deeply *understanding* your data before modeling — studying the relationship
between inputs and outputs. You can't build a good predictive model without first knowing
what's inside your data.

**Typical EDA activities:**
- **Univariate analysis** — study each column independently (distribution, spread, etc.)
- **Bivariate analysis** — study relationships between pairs of columns
- **Multivariate analysis** — study relationships among 3+ columns together
- Visualizations — plots/graphs to reveal patterns and relationships
- **Handling class imbalance** — e.g., in an image classification problem (cats vs. dogs) where
  one class has far more samples than the other, apply techniques to balance the dataset

> "If you're given 6 hours to cut down a tree, spend the first 4 hours sharpening the axe."
> The more time spent deeply understanding your data here, the easier every later
> decision becomes.

---

## 5. Feature Engineering & Feature Selection

**Features** = input columns. Since the output depends directly on the input features, this
stage is critical.

- **Feature Engineering** — creating new, more useful columns from existing ones.
  Example: instead of separate `number_of_bedrooms` and `number_of_bathrooms` columns for a
  house price prediction model, engineer a single `square_feet` column that better represents
  the same information.
- **Feature Selection** — dropping features that don't meaningfully affect the output. Too many
  irrelevant features slow down training without adding predictive value, so removing them
  reduces training time and can improve performance.

---

## 6. Model Training, Evaluation & Selection

With clean data and good features ready, you're set to train models.

**Model Training**
- Try **multiple algorithms**, generally from different families — no one algorithm is best for
  every kind of data (e.g., some algorithms work well on tabular data, others on text/images).
  You never know in advance which will perform best on your specific dataset, so you
  experiment with several.

**Model Evaluation**
- Evaluate each trained model using **performance metrics** to decide which performs best.
  - Classification problems → metrics like accuracy, precision, recall, F1-score
  - Regression problems → metrics like RMSE, MAE
  - Clustering problems → metrics like the Dunn Index

**Model Selection & Hyperparameter Tuning**
- Pick the best-performing model (or a few) and **tune its hyperparameters** — the model's
  internal settings — similar to adjusting picture mode/volume on a TV depending on what
  you're watching. Proper tuning further improves performance.

**Ensemble Learning (optional but powerful)**
- Combine multiple ML models into a single, more powerful model using techniques like
  **bagging, boosting, and stacking**. Ensembling frequently improves overall performance
  compared to any single model.

---

## 7. Model Deployment

Once you have a working, trained model, the real engineering work of turning it into an
actual product begins:

1. **Export the model** as a binary file (e.g., a pickle file), which stores the trained model
   in a compact, loadable format.
2. **Wrap it in an API** — the server-side app (e.g., a Python backend) receives user input
   (typically JSON from a web form), loads the binary model, generates a prediction, and
   returns the result (again typically as JSON) back to the frontend.
3. **Host it on a server/cloud platform** — e.g., AWS or GCP — so the model can serve
   real-time requests online.

---

## 8. Testing

Before a full public rollout:

- **Beta testing** — release the new model/feature to a small subset of trusted/loyal customers
  first (rather than all users at once) and gather their feedback.
- If feedback is positive → proceed to full deployment.
- If something's wrong → go back and revisit earlier stages (data quality, preprocessing,
  feature selection, or the algorithm itself may need fixing).

---

## 9. Optimization & Maintenance

Once fully deployed to all users, ongoing operational work continues:

- **Backups** — of both the model and the data, so you can roll back quickly if something breaks.
- **Load balancing** — distribute incoming requests efficiently to keep response times low
  under high traffic.
- **Retraining schedule** — decide how frequently to retrain the model. Models can suffer from
  **data/model drift** (performance degrading over time as real-world data patterns change),
  so retraining needs a deliberate, automated cadence — not manual, ad-hoc updates.
- **Automation** — automate as much of this pipeline as possible (retraining, backups, scaling)
  rather than repeating manual steps regularly.
- **Cost monitoring** — track where the pipeline incurs extra cost and optimize it.
